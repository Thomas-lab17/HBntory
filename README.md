# HBntory

Inventory-management system for a fictional retail company with several
branches. It combines two user-facing areas:

- **Backoffice** — authenticated internal users manage branch stock and
  users (admin).
- **Client Web Interface** — anonymous visitors ask natural-language
  questions about products and stock.

Product information always comes from the **external Product API**
(read-only). The local database stores only users, branches, and stock
quantities keyed by external product identifiers — never product metadata.

## Services

| Service | Port | Role |
|---|---|---|
| `client_web` | 8080 | Public chat (anonymous questions) |
| `backoffice-web` | 8081 | Backoffice UI (login / stock / users) |
| `api` | 5000 | Backoffice API (FastAPI + SQLite, JWT) |
| `ai` | 8100 | AI Query Service (DeepSeek agent + tools) |
| `product-mcp` | 8002 | MCP HTTP bridge to the external Product API |
| `external-products-api` | 5001 | External product catalog (read-only) |

## Setup

Prerequisites: Docker + Docker Compose.

```bash
# 1. Create .env from the template and set your keys
cp .env.example .env
#    → DEEPSEEK_API_KEY is required (https://platform.deepseek.com/api_keys)

# 2. Build and start the whole stack
docker compose up --build

# 3. Open
#    Backoffice:  http://localhost:8081
#    Client web:  http://localhost:8080
```

`.env` is gitignored: it never enters the repository. On a fresh clone you
MUST create it (step 1) or the `ai` service reports that the DeepSeek API key
is missing. For running the `ai` service outside Docker, export the variables
instead: `export DEEPSEEK_API_KEY="sk-..."`.

Optional environment overrides (all read from `.env` by Docker Compose):

| Variable | Default | Used by |
|---|---|---|
| `DEEPSEEK_API_KEY` | — (required) | `ai` |
| `DEEPSEEK_MODEL` | `deepseek-chat` | `ai` (LLM model) |
| `SECRET_KEY` | `change-me-in-production` | `api` (JWT signing) |
| `SERVICE_API_KEY` | `dev-service-key` | `api` + `ai` (must match) |
| `DATABASE_URL` | `sqlite:///./hbntory.db` | `api` (SQLite path) |
| `ADMIN_PASSWORD` | `admin` | `api` (initial admin) |

## Database initialization

On first boot the `api` container runs `python -m app.init_db`, which
creates the tables and seeds:

- one admin user (`admin`, password from `ADMIN_PASSWORD`),
- two branches (Paris, Lyon),
- sample stock rows using real external SKUs (e.g. `HB-LAP-1001`).

The SQLite file lives on a Docker volume (`backoffice-data`), so data
survives restarts.

## Backoffice usage

Open http://localhost:8081 and log in with `admin` / `admin` (or the value
of `ADMIN_PASSWORD`).

- **Admin** — manage users (list, create, edit, soft-delete) and branches
  (add new ones). Cannot touch stock.
- **Common user** — manage stock of their assigned branch only. Cannot
  manage users. Create one with the admin (role is forced to `common`).

## Client Web Interface usage

Open http://localhost:8080 and ask a question, e.g.:

- "Give me details about product HB-LAP-1001"
- "Which branch has stock of HB-LAP-1001?"
- "What products can I find in Lyon?"
- "Can I buy 2 of HB-LAP-1001 and 3 of HB-MON-2101 in one branch?"

Answers are generated by the AI agent from **real product and stock data**
via its tools; the agent never invents information and says clearly when
data is unavailable.

## Running each service individually

Each service can also be run outside Docker:

- **external-products-api**: `cd hbntory-products-api-main && docker compose up --build`
- **product-mcp**: `cd product_mcp_server && pip install -r requirements.txt && uvicorn app.main:app --port 8002` (set `PRODUCT_API_URL` to the catalog)
- **api**: `cd api && python -m venv .venv && .venv/bin/pip install -r requirements.txt && .venv/bin/python -m app.init_db && .venv/bin/uvicorn app.main:app --port 5000`
- **ai**: `cd ai_service && pip install -r requirements.txt && DEEPSEEK_API_KEY=... uvicorn app.main:app --port 8100`
- **backoffice-web** / **client_web**: static files served by nginx (see the Compose file)

## Main technical decisions

- **FastAPI + SQLAlchemy** for the Backoffice API (the project mandates
  SQLAlchemy); SQLite for development, switch to Postgres by changing only
  `DATABASE_URL`.
- **JWT bearer tokens (HS256, 12 h)** instead of server sessions:
  stateless and fits the JSON API. Every request re-reads the user from the
  DB, so a soft-deleted user's token stops working immediately and the
  branch always comes from the token, never from the client.
- **Werkzeug `scrypt`** for password hashing (salted, deliberately slow) —
  a general hash like plain SHA256 is fast to brute-force and unsuitable.
- **REST for the client** (not WebSockets): each question is independent
  and no history is kept, so request/response is simpler and stateless.
- **MCP bridge as the single integration point** for the external Product
  API: both the Backoffice and the AI service go through `product-mcp`
  instead of each keeping a direct client.
- **Controlled internal endpoint for AI stock access**:
  `GET /api/stock/product/{id}` guarded by `X-API-Key`, so the AI can read
  stock across branches without exposing the JWT-protected backoffice
  surface.
- **Product validation on stock operations**: `add_stock` checks the
  product exists in the external catalog (via the MCP bridge) and refuses
  unknown ids with a clear error.

## Known limitations

- The AI agent loop has no automated tests (the Backoffice API is covered
  by `api/tests/`).
- The external API is designed to simulate slowness and outages
  (`simulate_delay_ms`, `force_error`); the compose stack uses plain
  `depends_on` ordering, not health-checked startup.
- If the external API is temporarily unavailable, the backoffice falls back
  to raw product ids in the stock screen and stock additions are refused
  with a clear error.
